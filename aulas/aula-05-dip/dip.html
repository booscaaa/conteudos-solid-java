A Definição

O que diz o DIP?

format_quote

"Módulos de alto nível não devem depender de módulos de baixo nível.
Ambos devem depender de abstrações."

"Abstrações não devem depender de detalhes.
Detalhes devem depender de abstrações."

— Robert C. Martin

🏗️
Acoplamento Rígido
Regras de negócio criam suas próprias dependências com new. Trocar banco = alterar negócio.
🔌
Inversão via Abstrações
Negócio depende de interfaces. Infraestrutura implementa essas interfaces. Troca é cirurgia zero.
O Problema

O new que acopla 🔗

Acoplamento Rígido — PROBLEMA

class PedidoService { // Acoplado: cria as dependências com "new" private final MySQLPedidoDB db = new MySQLPedidoDB(); private final JavaMailSender mail = new JavaMailSender(); public void criarPedido(String id, double val) { db.save(id, val); // MySQL hardcoded mail.send(id, val); // JavaMail hardcoded } }

Consequências imediatas

Trocar MySQL → PostgreSQL
Exige abrir e alterar PedidoService. Regra de negócio muda por razão técnica.
Testar PedidoService
Precisa de MySQL real + servidor SMTP. Sem banco, sem teste.
Adicionar SendGrid
Exige if (provider == "sendgrid") dentro do serviço de negócio.
Conceito Central

Alto nível vs. Baixo nível

Módulo Nível Muda quando… Exemplos
PedidoService Alto Regra de negócio muda Use cases, Services, Domain
MySQLPedidoDB Baixo Tecnologia de banco muda Repositories, Clients, Adapters
JavaMailSender Baixo Biblioteca de email muda Email, SMS, Push providers
LDAPProvider Baixo Provedor de identidade muda LDAP, OAuth2, API interna
lightbulb Regra prática: se o nome da classe referencia uma tecnologia (MySQL, SMTP, S3, iText), é um módulo de baixo nível. Nunca instancie-o dentro do alto nível.
A Inversão

Quem define a interface?

Sem DIP — Infraestrutura manda

// MySQLPedidoDB define a API class MySQLPedidoDB { void save(Pedido p) { ... } Pedido findById(String id) { ... } } // PedidoService adapta para usar class PedidoService { private final MySQLPedidoDB db = new MySQLPedidoDB(); // acoplado ao método e nome da classe MySQL }

Com DIP — Domínio manda

// PedidoService define o contrato interface PedidoRepository { void salvar(Pedido p); Optional<Pedido> findById(String id); } // MySQLPedidoDB implementa o contrato class MySQLPedidoRepository implements PedidoRepository { ... } // O domínio manda. A infra obedece.
swap_vert A "inversão": antes, negócio se adaptava à infraestrutura. Com DIP, a infraestrutura se adapta ao negócio.

A Solução

Injeção de Dependências 💉

Abstrações + Injeção — SOLUÇÃO

// 1. Defina a abstração no domínio interface PedidoRepository { void salvar(Pedido p); } interface EmailService { void enviar(String dest, String msg); } // 2. Injete pelo construtor class PedidoService { private final PedidoRepository repo; private final EmailService email; public PedidoService( PedidoRepository repo, EmailService email) { this.repo = repo; this.email = email; } }

Composição no main (ou framework)

// Produção: MySQL + JavaMail PedidoService svcProd = new PedidoService( new MySQLPedidoRepository(), new JavaMailEmailService() ); // Teste: InMemory + stub silencioso PedidoService svcTest = new PedidoService( new InMemoryPedidoRepository(), (dest, msg) -> {} // lambda mudo ); // PedidoService não muda — só a composição
Técnicas

Formas de Injeção

1

Injeção pelo Construtor Recomendada

Dependências obrigatórias e final. Objeto nunca criado em estado inválido. Dependências visíveis na assinatura.

2

Injeção por Setter Para opcionais

Para dependências verdadeiramente opcionais ou configuráveis após construção. Requer cuidado com nulos.

✗

Service Locator Anti-pattern

Parece DIP mas esconde dependências dentro dos métodos. Difícil de testar. Erros só em runtime. Prefira construtor sempre.

🌱

IoC Container (Spring, Quarkus)

Framework realiza a composição automaticamente via @Autowired, @Inject. O princípio é o mesmo — o construtor ainda declara as abstrações.

Arquitetura

DIP em camadas

Arquitetura em Camadas — SEM DIP

Controller └── cria PedidoService └── cria MySQLRepository // ← acoplado └── new Connection() // ← acoplado // Seta sempre aponta para baixo e para concreto // Trocar MySQL = alterar TODAS as camadas acima

Arquitetura Hexagonal — COM DIP

Controller └── depende de PedidoUseCase // interface └── PedidoUseCaseImpl └── depende de PedidoRepository // interface └── MySQLPedidoRepository └── implements PedidoRepository // Setas apontam para interfaces (abstrações) // Trocar MySQL = criar novo impl, zero mudança acima
hub Na Arquitetura Hexagonal (Ports & Adapters), as ports são as interfaces definidas pelo domínio — DIP estrutural.
Como Identificar

Sinais de Violação do DIP

1

new MySQLAlgo() dentro de uma classe de negócio

O new cementa a dependência. Se está dentro do construtor com = new X(), há acoplamento.

2

Import de pacote de infra em camada de domínio

import com.mysql.* ou import org.springframework.mail.* dentro de um Service de negócio — red flag.

3

Testes de negócio precisam de banco ou SMTP real

Se não é possível testar a lógica sem infraestrutura real, o DIP foi violado — as dependências não são substituíveis.

4

Trocar tecnologia exige alterar regra de negócio

Se migrar de LDAP para OAuth2 força abrir e editar AutenticacaoService, o DIP está sendo violado.

5

Service Locator — dependências ocultas nos métodos

Quando as dependências não estão no construtor mas são buscadas dentro dos métodos, elas ficam invisíveis e difíceis de substituir em testes.

Conexões

DIP e os outros SOLID

S
SRP
Cada interface injetada tem uma responsabilidade — PedidoRepository só persiste pedidos. Coesão guia a definição das abstrações.
O
OCP
Adicionar SendGridEmailService não modifica PedidoService. DIP torna o OCP possível na prática.
L
LSP
Implementações injetadas devem ser substituíveis sem surpresas. Se PostgreSQLRepository quebra o contrato, o DIP não funciona.
I
ISP
Interfaces injetadas devem ser pequenas e coesas. Injetar uma interface gorda viola ISP e torna o DIP mais frágil.
link DIP é o princípio conector: os outros quatro definem como as peças devem ser — o DIP garante que elas se encaixem via abstrações.

Resumo

Dependency Inversion em 4 pontos

swap_vert

Dependa de abstrações, não de concretos

Declare as dependências como interfaces no construtor. Nunca new MySQLAlgo() dentro de um serviço de negócio.

domain

O domínio define os contratos

A interface PedidoRepository existe no domínio. O MySQLPedidoRepository existe na infraestrutura. A infra obedece ao domínio.

science

Testabilidade é consequência direta

Com DIP, basta injetar InMemoryRepository no teste. Nenhum banco real necessário para testar lógica de negócio.

extension

Trocar tecnologia sem tocar no negócio

MySQL → PostgreSQL: crie nova implementação, altere a composição. PedidoService não abre, não muda, não quebra.
