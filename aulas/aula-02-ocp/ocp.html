Definição

O que é o OCP?

format_quote

Entidades de software devem ser
abertas para extensão
mas fechadas para modificação.

— Bertrand Meyer, 1988 · popularizado por Robert C. Martin

lightbulb Em outras palavras: adicione funcionalidades novas sem alterar o que já funciona.
Primeira Parte

Aberto para Extensão

add_circle

Você pode adicionar novos comportamentos.

O sistema aceita crescer. É possível incluir novas funcionalidades, novos tipos de dados, novas regras — sem medo.

+ Nova forma geométrica + Novo tipo de pagamento + Novo canal de notificação
check_circle Extensão = criar classes novas, implementar interfaces, herdar de abstrações. O código novo se encaixa no sistema existente.
Segunda Parte

Fechado para Modificação

lock

Você não toca no código que já funciona.

Código testado e funcionando deve permanecer intocado. Cada modificação = risco de regressão — bugs em algo que já estava certo.

- Não editar if/else existente - Não modificar switch antigo - Não alterar lógica já testada
warning Modificar código existente sem OCP é como reformar a fundação de um prédio enquanto as pessoas ainda moram nele.

Vamos ao Código

O Cenário do Exemplo

Imagine um sistema que calcula a área de formas geométricas. Começamos com círculo e retângulo. Depois precisamos de triângulo...

circle
Círculo
π × r²
rectangle
Retângulo
largura × altura
change_history
Triângulo
(base × altura) / 2
question_mark Como adicionar triângulo sem quebrar o que já existe? A resposta depende de como você projetou o sistema.
Problema — Sem OCP

Violando o Princípio

// ❌ SEM OCP — Cada nova forma MODIFICA este arquivo! public class CalculadoraArea { public double calcular(String tipo, double a, double b) { if (tipo.equals("circulo")) { return Math.PI * a * a; // a = raio } else if (tipo.equals("retangulo")) { return a * b; // a = largura, b = altura } // ← Para triângulo: EDITAR AQUI! Risco de bug! return 0; } }
error Para adicionar triângulo, você abre este arquivo e edita o método. Código que funcionava pode quebrar.
O Diagnóstico

Por que isso é um Problema?

1

Cada nova forma = modificar código existente

Triângulo, losango, hexágono... todo novo tipo exige abrir e editar CalculadoraArea.

2

Risco de regressão a cada mudança

Um erro de digitação pode quebrar o cálculo do círculo que já estava perfeito.

3

Método cresce infinitamente

10 formas = 10 if/else. 50 formas = método ilegível. Manutenção vira pesadelo.

4

Dependência de String para identificar tipo

"Circulo" vs "circulo" — um erro silencioso retorna 0 sem avisar.

Solução com OCP — Passo 1

Criar a Interface Forma

A interface define um contrato: toda forma geométrica deve saber calcular sua própria área.

// ✅ Interface = contrato imutável public interface Forma { double calcularArea(); // Toda classe que implementar Forma // DEVE fornecer este método. }
contract A interface nunca muda. Ela é o ponto estável do sistema — a "tomada" que aceita qualquer plugue.
Solução com OCP — Passo 2

Cada Forma Implementa o Contrato

public class Circulo implements Forma { private double raio; public Circulo(double raio) { this.raio = raio; } @Override public double calcularArea() { return Math.PI * raio * raio; } }
public class Retangulo implements Forma { private double largura, altura; public Retangulo(double l, double h) { largura = l; altura = h; } @Override public double calcularArea() { return largura * altura; } }
Cada classe tem sua própria lógica de cálculo. Círculo sabe calcular círculo. Retângulo sabe calcular retângulo. Sem if/else!
Solução com OCP — Passo 3

Nova Forma — Zero Modificações

// ✅ Triângulo novo — não tocamos em NADA do código existente! public class Triangulo implements Forma { private double base, altura; public Triangulo(double base, double altura) { this.base = base; this.altura = altura; } @Override public double calcularArea() { return (base * altura) / 2; } }
check Círculo intocado check Retângulo intocado check Interface intocada add Triângulo: nova classe
Solução com OCP — Resultado

A Calculadora que Nunca Muda

// ✅ Este método existe desde o início e NUNCA precisou mudar! public class Calculadora { public double calcular(Forma forma) { return forma.calcularArea(); // delega para cada forma } } // ─── Usando ─────────────────────────────────────────────── Calculadora calc = new Calculadora(); System.out.println(calc.calcular(new Circulo(5))); // 78.54 System.out.println(calc.calcular(new Retangulo(4, 6))); // 24.0 System.out.println(calc.calcular(new Triangulo(3, 8))); // 12.0 // Amanhã: Losango, Hexágono... zero mudanças na Calculadora!
Polimorfismo em ação: o método calcular chama calcularArea() e cada objeto sabe o que fazer. Isso é o OCP.

Boas Práticas

Como Identificar e Aplicar

1

Viu um if/else ou switch para tipos? Suspeite!

Se o switch cresce a cada nova funcionalidade, é um sinal de violação do OCP.

2

Crie uma interface ou classe abstrata

Extraia o comportamento variável para um contrato comum que todas as variações seguirão.

3

Implemente cada variação em sua própria classe

Uma classe por comportamento. Pequenas, focadas, fáceis de testar e entender.

4

Pergunte-se: "Preciso editar código existente para adicionar isso?"

Se a resposta for sim, revise o design. Com OCP, a resposta deve sempre ser não.
