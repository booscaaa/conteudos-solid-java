Violação Clássica 1

O Pato de Borracha 🐥

Imagine: "se anda como pato e grasna como pato, é um pato." Mas e se for um pato de borracha que só grasna com pilha?

class Pato { void voar() { "voando!"; } void nadar() { "nadando!"; } void grasnar() { "quack!"; } } class PatoDeBorracha extends Pato { @Override void voar() { throw new UnsupportedOperationException("Não voa!"); } @Override void nadar() { throw new UnsupportedOperationException("Não nada de verdade!"); } }
warning Código que chama pato.voar() vai explodir com PatoDeBorracha. A subclasse mentiu sobre o que pode fazer.
Violação Clássica 2

Retângulo ≠ Quadrado no Código

Mundo Real

Matematicamente: Quadrado É um Retângulo (todos os lados iguais). Parece óbvio herdar, certo?

▭
Retângulo
largura ≠ altura
⊃
■
Quadrado
lado = lado

No Código — PROBLEMA

class Quadrado extends Retangulo { @Override void setLargura(double l) { largura = l; altura = l; // sobrescreve a altura! } @Override void setAltura(double a) { altura = a; largura = a; // sobrescreve a largura! } } Retangulo r = new Quadrado(); r.setLargura(5); r.setAltura(3); // Esperado: 5×3 = 15 // Real: 3×3 = 9 ← ERRADO!

Violação Silenciosa

Corpo Vazio é Pior que Exceção

Lançar exceção — ruim

class Pinguim extends Ave { @Override void voar() { throw new UnsupportedOperationException( "Não voa!" ); } }
Pelo menos o programa avisa que algo está errado.

Corpo vazio — PIOR

class Pinguim extends Ave { @Override void voar() { // "não faz nada, tá bom né?" } }
O programa não avisa. O código chama voar(), "funciona", mas o pinguim nunca voou. Bug silencioso.
warning Ambos violam o LSP. A violação silenciosa é a mais perigosa — o teste passa, o bug chega em produção.
Diagnóstico

instanceof = Sinal de Alerta

Se o código que usa a abstração precisa checar o tipo real, é porque a abstração falhou:

// ❌ Isso grita "LSP violado!" void fazerAveVoar(Ave ave) { if (ave instanceof Pinguim) { ((Pinguim) ave).nadar(); // precisou checar o tipo! } else { ave.voar(); } } // E quando aparecer Ema? Avestruz? Kiwi? // Mais um if/else — o método nunca fica estável.
error Regra prática: se você usa instanceof ou try/catch para usar uma subclasse no lugar da base, há violação de LSP.
O Problema das Aves

Hierarquia Honesta vs Mentirosa

Hierarquia mentirosa ❌

class Ave { void voar() { ... } // promessa! } class Pardal extends Ave { } // ok class Aguia extends Ave { } // ok class Pinguim extends Ave { void voar() { // MENTIRA — eu não voo! throw new RuntimeException(); } }

Hierarquia honesta ✓

interface Ave { void comer(); // toda ave come } interface Voadora { void voar(); // só quem voa } interface Nadadora { void nadar(); // só quem nada } class Pardal implements Ave, Voadora { } class Pinguim implements Ave, Nadadora { } // sem mentiras, sem exceções!

Regras Formais

Pré e Pós-Condições

input Pré-condição

O que a subclasse exige para funcionar. Nunca pode exigir mais que a superclasse.

✓

Base aceita: valor > 0

Sub aceita: valor >= 0 → OK (mais permissiva)

✗

Base aceita: valor > 0

Sub aceita: valor >= 100 → VIOLA (mais restritiva)

output Pós-condição

O que a subclasse garante após executar. Nunca pode garantir menos que a superclasse.

✓

Base garante: saldo aumenta

Sub garante: saldo aumenta E notifica → OK

✗

Base garante: saldo aumenta

Sub pode não aumentar o saldo → VIOLA

lightbulb Analogia: o contrato de entrega promete "3 dias". A sub pode entregar em 1 dia (melhor), mas nunca em 7 dias (pior).
A Solução

Interfaces de Capacidade

Em vez de herdar de uma superclasse com comportamentos que nem todos podem cumprir, componha interfaces pequenas por capacidade.

interface Ave { void comer(); void emitirSom(); } interface AveVoadora { void voar(); } interface AveNadadora { void nadar(); } interface AveCorredeira { void correr(); } // Cada classe implementa só o que REALMENTE pode fazer class Pardal implements Ave, AveVoadora { } class Pinguim implements Ave, AveNadadora { } class Pato implements Ave, AveVoadora, AveNadadora { } class Ema implements Ave, AveCorredeira { } // Código que usa só aves voadoras — NUNCA vai receber Pinguim void realizarVoo(AveVoadora ave) { ave.voar(); }
Exemplo Real

Conta Somente Leitura

Viola LSP ❌

class ContaBancaria { void depositar(double v) { ... } void sacar(double v) { ... } } class ContaSomenteLeitura extends ContaBancaria { @Override void depositar(double v) { throw new UnsupportedOperationException(); } @Override void sacar(double v) { throw new UnsupportedOperationException(); } }

Respeita LSP ✓

// Separamos as capacidades interface Conta { double getSaldo(); String getTitular(); } interface ContaOperavel extends Conta { void depositar(double v); void sacar(double v); } // Conta corrente: pode tudo class ContaCorrente implements ContaOperavel { } // Só leitura: não mente sobre sacar/depositar class ContaVisualizacao implements Conta { }

Como Identificar

Sinais de Violação do LSP

!

Método lança UnsupportedOperationException

A subclasse prometeu algo que não pode cumprir.

!

Método sobrescrito com corpo vazio

Pior que exceção — bug silencioso que não aparece nos testes.

!

Código cliente usa instanceof

Quem usa a abstração precisou saber o tipo real — hierarquia falhou.

!

Resultado diferente do esperado sem exceção

Área 9 quando esperava 15. O contrato foi quebrado silenciosamente.

!

Subclasse mais restritiva na entrada

Base aceita qualquer valor > 0; sub exige valor >= 100.

Conexão com SOLID

LSP + OCP = Hierarquias Poderosas

extension OCP garante:

Você pode adicionar novos tipos sem modificar o código existente. Extensão via novas classes.

swap_horiz LSP garante:

Essas novas classes podem ser usadas em qualquer lugar que a base era usada. A extensão é segura.

O OCP diz "adicione sem modificar".
O LSP garante que o que foi adicionado funciona onde esperado.
Juntos: você cresce o sistema com confiança total.

Armadilhas Comuns

🔀
"É-um" do mundo real ≠ herança
Quadrado É um Retângulo na matemática, mas no código têm comportamentos incompatíveis. Modele pelo comportamento, não pela categoria real.
🤫
Violação silenciosa
Corpo vazio não gera exceção mas quebra a lógica. Pode passar em todos os testes e só aparecer em produção.
🏗️
Herança profunda
Hierarquias de 4+ níveis acumulam contratos que ficam cada vez mais difíceis de honrar. Prefira composição.
📌
Sub mais restritiva
Adicionar validações extras na subclasse (valor mínimo, tipo obrigatório) que a superclasse não exigia viola a pré-condição.

L

Princípio

Subclasse deve poder substituir a superclasse sem que o programa precise saber.

!

Sinais de Problema

UnsupportedOperationException · corpo vazio · instanceof · resultado errado sem exceção

✓

Solução

Interfaces pequenas de capacidade · modelar por comportamento, não por "é-um" · preferir composição

Regras Formais

Pré-condição: nunca mais restritiva · Pós-condição: nunca garante menos · Invariante: propriedades sempre mantidas
